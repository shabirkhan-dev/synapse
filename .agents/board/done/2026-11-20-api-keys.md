## What

A user creates named API keys (shown once, stored hashed) that call the API as them in one organization, and can revoke them.

## Why / Context

Gap review 2026-11-19 (item 5): the API can only be used through the console's session.

## Proposal or Ask

`Authorization: Bearer syn_...` accepted next to access tokens; keys scoped to user + organization, last-used time, revoke; same rate limits; audited. Done with API tests and an Account page section.

## Scope

**In scope:** packages/database, packages/security, apps/api auth, apps/console account.

## Validation

- lint, typecheck, unit and integration tests, e2e where a flow changes

## Resolution

Migration 0021 `api_keys`. `ApiKeysService` + `DrizzleApiKeyRepository` in the auth module:
create (shown once, active organization, optional expiry, ≤ 20), list, revoke; `authenticate` checks
hash, expiry and the user's live role there (`401 AUTH_NOT_A_MEMBER` after leaving), touches
`last_used_at` at most once a minute. The auth middleware sends `syn_…` bearers to it; a
session-only middleware refuses keys on sign-out, sessions, switch-organization and api-keys.
`AuthUser.via` says which. Console: "API keys" card on Account (create, copy once, revoke).

Validation: API 4 new tests (key acts in its team as its user, hidden after creation, last used;
session-only routes refused; revoked and left-team keys stop; expiry; 20-key cap) + Postgres
repository test; console card test; e2e (create in the browser, call the API with it, revoke → 401).
